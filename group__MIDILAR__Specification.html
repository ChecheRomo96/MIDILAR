MIDI-Domain Specification

Invariants every MIDILAR type follows, written before the code.

Invariants every MIDILAR type follows, written before the code.

Each invariant has a stable identifier referenced from the unit tests that prove it, as in MCC's music-domain specification.

Scope

  • MIDILAR owns MIDI protocol data: MIDI 1.0 byte streams, MIDI 2.0 Universal MIDI Packets (UMP), channels and groups, notes, velocities, controllers, system common, real-time, MTC and System Exclusive; parsing and encoding; routing; timing; and devices that transform message streams. MIDI-CI follows in a later phase.
  • Music theory (pitches, spelling, scales, chords, keys) belongs to MCC. MIDILAR converts between note numbers and MCC::Pitch with explicit range checks, and spells incoming notes through MCC::Key.
  • General utilities (buffers, callbacks, time, scheduling, flash data) belong to Foundation. Signal processing belongs to the future DspCore.

Design rules

  • SPEC-RT-1: Real-time paths (parsing, routing, devices) never allocate memory dynamically and never throw exceptions.
  • SPEC-RT-2: Value types are trivially copyable, with size budgets checked at compile time for every target (src/MIDILAR.cpp).
  • SPEC-RT-3: Every value type with spare bit patterns has one canonical invalid value; invalid input produces it instead of undefined behavior. Full-width types (masks, 16-bit velocity, 32-bit values) use every bit pattern and have no invalid value; their MIDI 1.0 constructors clamp.
  • SPEC-RT-4: Variable-length data (System Exclusive) is read from and written to caller-provided buffers.
  • SPEC-RT-5: Constant tables live in program memory on AVR through FOUNDATION_FLASH.

Internal model

  • SPEC-MIDI-1: The internal message model is the MIDI 2.0 Universal MIDI Packet: 32-, 64-, 96- and 128-bit packets with a message type and a group. Devices, routing and timing work on UMP only.
  • SPEC-MIDI-2: MIDI 1.0 byte streams (DIN/UART, USB MIDI 1.0) are translated at the edges: a parser turns bytes into UMP and an encoder turns UMP back into bytes, following the MIDI 2.0 translation rules.
  • SPEC-MIDI-3: Values are kept at MIDI 2.0 resolution: 16-bit velocity and 32-bit controller, pressure and pitch-bend values. MIDI 1.0 values are scaled up with the specification's min-center-max rule and scaled down by keeping the most significant bits, so a 1.0 value survives a round trip.

Channels, groups and values

  • SPEC-MIDI-4: Channel and Group store the wire and UMP value 0-15. They are built only through named constructors, FromWire(0-15) and FromNumber(1-16), and read back through Wire() and Number(), so the numbering is always explicit. Any other input is the invalid value, and a valid Channel or Group is always one a message can carry.
  • SPEC-MIDI-5: Omni and "every group" are not channel or group values. Filters, receivers and routes use ChannelMask and GroupMask, 16-bit sets with All(), Only(), union and intersection; Omni is ChannelMask::All().
  • SPEC-MIDI-6: NoteNumber, ControllerNumber and ProgramNumber are 7-bit values in [0, 127] in both protocols, with one invalid value each.

Notes and pitches

  • SPEC-MIDI-7: Note number n equals MCC::ChromaticIndex(n): MIDI 60 is C4 and MIDI 69 is A4. Converting a pitch outside [0, 127] yields the invalid note number; converting a note number yields a pitch spelled by an MCC::Key (default: C major).
  • SPEC-MIDI-8: A MIDI 1.0 Note On with velocity 0 becomes a Note Off with velocity 0 when it enters MIDILAR, so consumers see one release message kind. A MIDI 2.0 Note On with velocity 0 stays a Note On, as the MIDI 2.0 protocol defines.

MIDI 1.0 byte-stream rules

  • SPEC-MIDI-9: A byte with bit 7 set is a status byte; every data byte is in [0, 127], including System Exclusive data.
  • SPEC-MIDI-10: Running status is always accepted on input: after a channel message, data bytes without a new status reuse the previous channel status. System common messages and System Exclusive clear running status; real-time messages do not. The encoder writes full status bytes by default, and running status on output is an explicit option.
  • SPEC-MIDI-11: Real-time bytes (0xF8-0xFF) may appear anywhere, including inside another message or a System Exclusive message; they are delivered immediately and leave the interrupted message intact.
  • SPEC-MIDI-12: A status byte that arrives where a data byte was expected aborts the incomplete message and starts the new one. Undefined status bytes (0xF4, 0xF5, 0xF9, 0xFD) are ignored.

System Exclusive

  • SPEC-MIDI-13: A MIDI 1.0 System Exclusive message runs from 0xF0 to 0xF7; any other defined status byte that is not real-time also ends it, and the payload so far is delivered as its last packet. In UMP it travels as 7-bit System Exclusive packets (six data bytes each); 8-bit System Exclusive uses its own UMP packets.
  • SPEC-MIDI-14: System Exclusive payloads are assembled into a caller-provided buffer. When the payload does not fit, the first bytes are kept, the message is flagged as truncated and reading continues to the end of the message, so the stream stays synchronized without allocating. Chunked delivery for very large payloads may be added later.

UMP packets

  • SPEC-MIDI-16: A Packet holds one to four 32-bit words; its size follows the message type (0-2, 6-7: 1 word; 3-4, 8-A: 2; B-C: 3; 5, D-F: 4). Utility and stream messages carry no group.
  • SPEC-MIDI-17: Named constructors produce the exact bit layouts of the UMP specification, and every query returns what its constructor stored.
  • SPEC-MIDI-18: A MIDI 1.0 Note On packet never carries velocity 0; a velocity that scales down to 0 is sent as 1.
  • SPEC-MIDI-19: Invalid constructor arguments produce the invalid packet; queries on packets of another kind return the invalid value, or zero or the minimum for types without one.

Devices

  • SPEC-DEV-1: A device processes one packet at a time and emits zero or more packets through a Foundation::Functional::Callback output, with no virtual functions and no allocation. An unbound output drops packets, and devices never emit the invalid packet.
  • SPEC-DEV-2: Note devices (transpose, scale filter) apply to every packet addressed to a note, MIDI 2.0 per-note messages included, and drop a packet whose note would leave [0, 127].
  • SPEC-DEV-3: A note keeps the output note it started with until its Note Off, even when the device's mapping changes meanwhile, so devices never leave notes hanging; a dropped Note On also drops its Note Off.

MIDI clock

  • SPEC-CLK-1: MIDI clock runs at 24 timing clocks per quarter note. A generator schedules each clock from the previous due time with exact rational arithmetic on the Foundation::Time::Clock frequency, so the tempo does not drift; after a stall it drops the backlog instead of bursting more than one beat of clocks.
  • SPEC-CLK-2: Start plays from position zero, Continue resumes, Stop pauses and keeps the position, and Song Position (in sixteenth notes, six clocks each) moves it only while stopped. Timing clocks advance the position only while running.
  • SPEC-CLK-3: A receiver follows the same transport rules from incoming packets and measures the tempo from the time between timing clocks.

Sequencing

  • SPEC-SEQ-1: EuclideanPattern(k, n) spreads k onsets over n <= 64 steps so that gaps differ by at most one step; it starts on an onset and equals Bjorklund's pattern up to rotation.
  • SPEC-SEQ-2: A step sequencer advances only on timing clocks while the transport runs, starts a step every ClocksPerStep clocks from Start or Song Position, and releases every note it starts (after its gate, at the next onset, or at Stop).

MIDI Time Code

  • SPEC-MTC-1: A TimeCode is hh:mm:ss:ff at 24, 25, 29.97 drop-frame or 30 fps. At 29.97 drop-frame, frames 0 and 1 are skipped at the start of every minute not divisible by ten, so ten minutes are exactly 17982 frames. Quarter-frame pieces 0-7 carry the frames, seconds, minutes and hours nibbles, the last one with the rate.
  • SPEC-MTC-2: A generator sends four quarter frames per frame; the eight pieces of a message describe the frame in which piece 0 was sent. It is timed with exact rational arithmetic (29.97 is 30000/1001 fps), so the time code does not drift. A full frame is F0 7F 7F 01 01 hr mn sc fr F7, with the rate in bits 6-5 of hr.
  • SPEC-MTC-3: A receiver takes a time from eight in-order quarter frames, adding the two frames they take to arrive, or from a full frame; out-of-order pieces restart the assembly.

USB MIDI 1.0

  • SPEC-USB-1: A USB MIDI 1.0 event (cable and Code Index Number, then up to three bytes) maps to one packet on the group equal to the cable. System Exclusive events become 7-bit System Exclusive packets of up to three bytes whose position comes from the 0xF0 and 0xF7 they carry, so decoding needs no state. Reserved and malformed events are rejected.
  • SPEC-USB-2: Packets are encoded through their MIDI 1.0 bytes onto the cable equal to their group; System Exclusive bytes that do not fill an event wait for the next packet of the same message on that cable.

Diagnostics

  • SPEC-MIDI-15: Error counters (aborted messages, ignored bytes, truncated System Exclusive) exist only when the build enables the MIDILAR_PARSER_DIAGNOSTICS option; by default the parser keeps no counters and spends no memory on them.
